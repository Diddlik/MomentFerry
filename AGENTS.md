## Project facts

- Purpose: Self-hosted service that discovers synchronized photos and videos, matches capture timestamps to events, and safely routes media from source shares to shared destinations.
- Primary languages and runtimes: C# on .NET 10 / ASP.NET Core; browser UI in plain JavaScript, HTML, and CSS; SQLite persistence.
- Important entry points: `src/MomentFerry.Web/Program.cs` composes the API and workers; `src/MomentFerry.Web/wwwroot/app.js` drives the Web UI; `src/MomentFerry.Web/Background/MediaRoutingWorker.cs` runs automated routing.
- Build command: `dotnet build MomentFerry.sln -c Release --no-restore -m:1` after `dotnet restore MomentFerry.sln`.
- Test command: `dotnet test MomentFerry.sln -c Release --no-build -m:1` after a successful Release build.
- Single test command: `dotnet test tests/MomentFerry.Tests/MomentFerry.Tests.csproj -c Release --no-build -m:1 --filter FullyQualifiedName~SafeTransferServiceTests`.
- Lint and format command: `dotnet format MomentFerry.sln --verify-no-changes --no-restore`.
- Local run command: `dotnet run --project src/MomentFerry.Web/MomentFerry.Web.csproj -c Release --no-build --urls http://127.0.0.1:5080`.
- Required environment: .NET 10 SDK for development; ExifTool for local metadata extraction; Docker with Compose for the supported container deployment. Mounted source and destination paths must be readable or writable according to their configured roles.
- Module map: `MomentFerry.Core/Domain` holds entities and enums only; `MomentFerry.Application/Services` holds the routing and transfer use cases (`SafeTransferService`, `TransferCoordinator`, `RoutingPreviewService`, `OperationRecoveryService`); `MomentFerry.Infrastructure` holds SQLite repositories, ExifTool metadata, and the filesystem gateway; `MomentFerry.Web/Api` holds minimal-API endpoint groups and `MomentFerry.Web/Background` the workers.
- Architecture constraints: Dependencies flow from Core to Application to Infrastructure to Web. Core must not depend on ASP.NET, MQTT, ExifTool, or persistence infrastructure. Filesystem paths are the sync-tool-agnostic integration boundary. Safe Move may delete a source only after the destination is committed and its size and SHA-256 match. Bounded routing cycles use persisted `media_files.last_seen_at` values to prioritize unindexed, then least-recently evaluated files; creating, editing, or deleting an event requeues already-indexed media inside the affected capture window by resetting `last_seen_at`, so a late-defined event is applied on the next cycle instead of waiting for the sweep; Synology `@eaDir` metadata is excluded from discovery. The update UI treats the install-request connection drop as an expected restart, waits for the requested running version and reloads itself.
- Generated files: `bin/`, `obj/`, local SQLite databases, `data/runtime-settings.json`, and `data/automation-status.json` are build or runtime outputs.
- Files or directories not to edit manually: Do not edit `bin/`, `obj/`, SQLite database files, or persisted runtime settings by hand. Add schema changes through the versioned migration code documented in `docs/DATABASE-MIGRATIONS.md`; the current schema version is 5.
- Platform-specific constraints: The production Docker image is Linux-based and includes ExifTool and `tzdata`. `tzdata` is installed explicitly rather than relying on the base image: without it .NET resolves no named zone, so `TZ` and a share's configured zone would both fall back to UTC, and the capture time of a photo whose EXIF states no offset depends on that zone. Verified on the running container that `Europe/Berlin` does resolve; whether it resolved before `tzdata` was added explicitly was never tested, so do not cite the package as the cause of a wrong capture time. Zone lookups are guarded and fall back to UTC rather than throwing, because an unresolvable zone would otherwise kill the routing cycle on its first photo. Development is supported on Windows; keep path handling platform-neutral and validate mounted container paths. Use serial .NET build/test commands on Windows to avoid intermittent file-lock contention.
- UI task behavior: Long-running browser actions use the global background-task tracker so in-app navigation does not hide progress or allow duplicate starts. Tasks do not persist across a manual browser reload or a closed tab.
- Share media rules: a source share stores its own image and video extension lists; an empty list falls back to `MediaExtensionDefaults`, so clearing the field cannot silently stop discovery. Excluding a media type entirely is done with the share's allowed media types, not by emptying its extensions. A destination share may set `ImageSubfolder`/`VideoSubfolder`, appended below the event folder by `DestinationPathResolver`; unset keeps photos and videos together. Subfolder segments are sanitized and validated as relative paths.
- File naming: `RenamePreset` rows hold filename templates rendered by `FileNameTemplate`. A source share's preset runs first and a destination share's preset then runs over its result, so the source normalizes the incoming name and the destination shapes the stored one. Extensions are never templated; they are carried from the source file. A `{seq}` token makes `DestinationPathResolver` probe the target folder for the first free number, while `SafeTransferService` remains the final collision authority. `CameraMapping` rewrites raw EXIF models (CPH2581 to OnePlus12) for the `{camera}` token. Empty tokens collapse along with their leftover separator, and a template that renders empty falls back to the original stem.
- Destination timestamps: after the destination is verified, `SafeTransferService` stamps it with the media's capture time through `IFileSystemGateway.SetFileTimestampsUtc`, so galleries that sort by file date match the shooting order instead of the copy time. Linux cannot set a birth time, so the container run stamps the last-write time only. A refused stamp never fails a verified copy; it is reported in the transfer result message.
- Copy durability: `CopyFileAsync` writes without `FileOptions.WriteThrough` and calls `Flush(flushToDisk: true)` once when the file is complete. WriteThrough maps to `O_SYNC` on Linux and made every 128 KB write wait for the disk: 1.3 MB/s measured against 208 MB/s for the same data flushed once on a Synology volume. The single fsync still returns only once the bytes are on disk, and it runs before the staging file is read back for verification, so the transfer guarantees are unchanged.
- Duplicate content already at the destination: right after the source hash is computed, and before the destination path is resolved, `SafeTransferService` asks `FindByDestinationHashAsync` where that exact content was written, then stats and re-hashes **that file on disk** — the record only supplies the path, the bytes decide, so a destination copy that was renamed, changed or lost never stops a transfer. A verified hit is handled as an identical destination, which means the event's `DuplicateStrategy` decides: `SafeMoveToExisting` removes the source, anything else keeps it. The check deliberately does not depend on a name collision, because the name a file renders to now need not be the name it was stored under: a changed preset, a changed camera mapping or a taken sequence number all produce a different one, and a path-only check then wrote the same content a second time under the new name and deleted the returned file. Superseded operations count as well, since an event route-again marks every finished operation `Failed` and that is exactly the moment its files are all transferred again; states that never committed a destination are excluded, because a verification quarantine can carry the hash of a staging file. Content that two devices contributed independently is indistinguishable from a returned copy by hash alone, and both resolve the same way: one copy is stored, the other source follows the duplicate policy.
- No terminal-state guard: a finished (`Completed`/`Ignored`) operation does not stop a media file from being routed again. Whether a file still has to move is a question about bytes, and `SafeTransferService` answers it: it finds the content by hash wherever it was stored, re-hashes that file on disk, and lets the event's `DuplicateStrategy` decide, while differing content gets a name of its own through the `ConflictStrategy`. The coordinator once asked instead whether *some* file occupied the recorded `DestinationPath`. That answered a different question: once anything else came to sit under that name — another photo routed there after the first copy was moved away — the source was counted as "already routed" for good, with its bytes nowhere at the destination. The cost of dropping it is a full SHA-256 read of every source that lingers in a share on every cycle; under Safe Move sources are released, so this bites only in `Copy` mode. A source that has already been released is not an error: `TransferCoordinator` turns `FileNotFoundException` into a plain refusal.
- Reported vs. inferred offset: `MediaMetadata.ReportedUtcOffset` is set only when the file itself states the offset it was taken at — `OffsetTimeOriginal`, a `CreationDate` carrying one, or `SamsungAndroidUtcOffset`. It is a different question from `TimeZoneInferred`: a QuickTime `MediaCreateDate` is a certain instant in UTC whose wall-clock offset is unknown, so it is `TimeZoneInferred = false` with no reported offset. Only a reported offset is persisted to `captured_at_offset_minutes`; recording zero from a QuickTime instant pinned UTC and named a 15:10 recording `131000`, and stopped the share's zone from ever standing in.
- Capture time vs. the name it renders: `media_files.captured_at_utc` is the absolute instant, because `ListMatchableAsync` and `RequeueByCaptureWindowAsync` compare it as text and mixed offsets would break both. Normalising to UTC dropped the offset EXIF reported, and `FileNameTemplate` formats a `DateTimeOffset` in its own offset, so every name and every `{year}/{month}/{day}` folder came out in UTC — a Samsung photo taken at 13:52:53 with `OffsetTimeOriginal +02:00` was stored as `20260821_115253`, and shots between midnight and the zone offset filed under the previous day. `captured_at_offset_minutes` (schema 5) keeps the reported offset beside the instant, and `DestinationPathResolver.LocalCapture` applies it when rendering; a row without one falls back to the source share's zone, which inverts the same assumption the extractor makes on the way in. `RoutedFileRenameService` backfills the offset by reading the stored copy, since a Safe Move source is usually gone, and refuses to record an inferred one. Every writer of `MediaFile` must carry the column through: the upsert assigns it rather than `COALESCE`ing it, so forgetting it blanks the offset.
- Renaming stored files: `POST /api/v1/events/{id}/rename-routed` re-applies the current naming rules to the files an event already stored, because renaming happens on the way to the destination and a preset or camera mapping added later never reached them — and a route-again cannot reach them either once Safe Move released their sources. `RoutedFileRenameService` walks the event's `Completed` operations, re-resolves each destination through `DestinationPathResolver` and renames the committed file in place, then persists the new `DestinationPath` so the history keeps pointing at the copy it verified. Two conditions must hold before anything moves: the target name must be free, and the file on disk must still hash to the operation's `DestinationHash`. The hash is what makes the record honest — carrying a `Completed` operation over to a new name without re-proving the bytes would hand a replaced or damaged file a verification it never earned — and it is read only for files that are actually about to move, so a library whose names already match costs nothing. An operation without a recorded hash is skipped rather than trusted. The resolver is handed a gateway that hides the file's own path, otherwise a `{seq}` template would step every file to the next free number on each run. The transfer's conflict strategy is deliberately not applied: inventing a second name for a file that is already stored correctly is not a fix. Under Dry Run the endpoint reports the plan — including checksum mismatches, so the preview matches what a real run would do — and touches nothing. It refuses while an automation cycle is running, since a cycle may be committing into the same folder.
- Route again: `POST /api/v1/operations/{id}/route-again` re-routes one file whose operation already reached `Completed` or `Ignored`, and `POST /api/v1/events/{id}/route-again` does it for a whole event: it calls `SupersedeTerminalByEventAsync`, which marks every finished operation of that event `Failed` in one statement, then queues the normal backfill. Held and retry-pending operations are left untouched, so a route-again cannot bury a decision the user still owes. It differs from a plain backfill in the history it leaves: the superseded records stop claiming to own the files they wrote. Files the earlier runs wrote stay where they are. Both entry points require Live mode; the event one also requires automation enabled and an idle cycle.
- Container tags: the container workflow publishes `latest` only from a `v*` tag and `edge` from `main`, both alongside `sha-<commit>`. `{{is_default_branch}}` in `docker/metadata-action` is also true for a tag push, so gating `latest` on it let the branch run and the tag run race for the same tag; when the branch run won, `latest` carried the `0.0.0-dev.<run>` stamp and the in-app updater waited for a release version that never arrived.
- Camera identity: phone videos usually carry no `Make`/`Model`. The extractor also requests `AndroidManufacturer`/`AndroidModel` (the `com.android.*` QuickTime keys), `OplusProductModel` (OnePlus writes no `Make`, no `Model` and no `com.android.model`, only `com.oplus.product.model`, which already holds the marketing name `OnePlus 12`), `SamsungModel` (a maker note, e.g. `SM-S921B`) and `Author` (Samsung's `udta/auth`, e.g. `Galaxy S24`). `ResolveModel` prefers `Model`, then `AndroidModel`, then `OplusProductModel`, then the marketing name from `Author` but only when `SamsungModel` proves who wrote the file, because `Author` is free text everywhere else. That keeps a video named like a photo from the same phone. A non-zero ExifTool exit whose output still parses as JSON is used rather than discarded, so an unknown tag name costs a warning instead of every field.
- Camera mapping: `FileNameTemplate.ResolveCamera` collapses whitespace runs in the reported model, tries an exact mapping match, then matches a mapping key **inside** the model. Video containers pad the model out with the maker and the lens (`OnePlus  CPH2581 23mm`), and the focal length changes with the lens while the model code does not, so an exact-match-only table would need one entry per lens. The longest key wins, ties fall back to key order.
- Capture time: video candidates are `CreationDate`, `MediaCreateDate`, `CreateDate`, `TrackCreateDate` in that order. `CreationDate` carries the recording's own UTC offset, so it needs no assumption. The other three are UTC by QuickTime specification and arrive without an offset; they are read as UTC, and `SamsungAndroidUtcOffset` re-expresses the same instant in the zone the recording was made in. `TryParseWithOffset` refuses a value that carries no offset: the `K` format specifier matches an empty offset and silently attaches the process zone, which shifted every video by the container's UTC offset while reporting `TimeZoneInferred = false`. A photo's `DateTimeOriginal` really is local wall-clock time, so the share zone stays the fallback there and is still reported as inferred.
- Maintenance: `/api/v1/maintenance` serves a Maintenance view with manual-only actions. `reindex-metadata` clears `source_last_write_at_utc` (per share or all) so the next cycle extracts metadata again — routing reuses the index only while size and last-write time match, so this is the only way a corrected extractor reaches files already indexed. `forget-missing` removes index rows whose source file is gone, skipping any row an operation refers to, because the foreign key is `ON DELETE CASCADE` and would take the operation history with it. `prune-operations` and the `OperationRetentionDays` setting (0 = keep for good, applied by the periodic full reconcile) remove only terminal operations older than the window; `Quarantined` and `RetryPending` are never removed, so a retention window cannot bury an unresolved file. `compact` runs `VACUUM`.
- Automatic image updates: `ImageUpdateWorker` checks shortly after start (`MomentFerry:Updates:InitialDelaySeconds`, default 30), then waits on `ImageUpdateWakeSignal` for up to 6 hours, and installs through the updater companion when a newer stable release exists. Both halves matter: with a bare 6-hour timer a container restarted more often never checked at all, and enabling the toggle on a running container did nothing until the period that was already running happened to end — `PUT /api/v1/settings` therefore wakes the worker on the transition from off to on only, so saving unrelated settings does not re-check. Every pass logs its outcome — nothing to install, no updater configured, install requested, or the failure — because a release that silently never arrives is otherwise indistinguishable from a broken toggle. `updaterConfigured` requires both `WatchtowerUrl` and `WatchtowerToken`; without them the check still runs and reports the available version but nothing is installed. The Web UI asks for no confirmation before installing: the button only exists while an update is available and names the version, so it sends `ImageUpdateRequest.RequiredConfirmation` itself. The API keeps requiring that token, which is a guard against a stray request, not a user prompt.
- Metadata processing: Routing reuses indexed capture metadata only when source size and last-write time still match. New or changed files use bounded ExifTool parallelism from runtime settings (default 2, range 1-8); SQLite matching and transfers remain controlled. Full-file SHA-256 reads remain mandatory for Safe Move verification.
- Wake types: `AutomationWakeSignal` distinguishes a targeted wake from a full reconcile. The filesystem watcher carries the changed path, so the routing worker evaluates just that file through `ShareDiscoveryService.Observe` and `RoutingPreviewService.EvaluateAsync` without walking the share. A full walk (`PreviewAsync`) runs only on the periodic schedule, on manual runs, on watcher errors, and when pending paths for one share exceed 1000 — targeted evaluation does not apply `MaxFilesPerSharePerCycle`, so overflow deliberately falls back to the bounded walk. The worker tracks the last full reconcile independently of its wait loop, stamping it after the cycle so the interval is a rest gap and steady watcher traffic cannot postpone the sweep.
- Event backfill: `POST /api/v1/events/{id}/backfill` queues a full pass over that event's source shares and routes every stable file whose capture time falls in the event window, reading metadata for files that are not indexed yet. It runs on the same single-reader worker, is not capped by `MaxFilesPerSharePerCycle`, and filters matches to the requested event so it cannot move media belonging to another event. Like the manual scan it requires automation enabled and an idle cycle.
- Web UI language: `wwwroot/i18n.js` picks the language from `localStorage` (`momentferry.language`), then `navigator.languages`, then English, and `document.write`s the matching `wwwroot/i18n/<code>.js` so `t()` is usable while the renderers run. Translation keys are the English source strings, so a missing entry renders English. Static markup carries no annotations: `initI18n()` walks text nodes plus `placeholder`/`title`/`aria-label` and looks each up. Changing the language reloads the page. Adding a language means adding one `wwwroot/i18n/<code>.js` and one `LANGUAGES` entry; `TranslationCatalogTests` fails if a catalog does not match `de.js` key for key. Server-sent enum values and worker phases are translated through the same `t()` fallback, so their English names are catalog keys.
- Access protection: `PasswordProtectionEnabled` is persisted as a runtime setting, but the username and password come only from `MomentFerry__Authentication__Username` and `MomentFerry__Authentication__Password` (the Compose example maps them from `.env`). The password must contain at least 12 characters. When enabled, middleware protects the Web UI, REST API, OpenAPI documentation and metrics with a signed HttpOnly SameSite cookie and disables response caching; `/health`, the login assets and authentication status/login endpoints remain public. Unsafe API requests require `X-MomentFerry-Request: 1` to prevent cookie-based CSRF, and login attempts are rate-limited. Enabling is refused until both credentials are configured. Public exposure still requires HTTPS because authentication does not encrypt plain HTTP traffic.
- Blocked operations: `RetryPending` and `Quarantined` both keep their media file unroutable (`GetIncompleteByMediaFileAsync`) until a user acts, so `GET /api/v1/quarantine` returns both and the "Needs your decision" card offers Retry for both and Dismiss only for `Quarantined`. Startup recovery logs every operation it leaves in a non-terminal state, and each automation cycle logs its trigger (full reconcile vs. watcher path count), duration, and the reason a matched file was not routed.
- Log volume: every refusal the routing worker reports is one line per file. The bulk case that once needed aggregating — a sorted share refusing hundreds of already-routed files per cycle — no longer exists, because a finished operation no longer refuses anything.
- Activity log: `ActivityLogProvider` is registered as a logging provider and mirrors `MomentFerry.*` records at Information and above into the bounded in-memory `ActivityLog` (default 500 entries, `MomentFerry:ActivityLog:Capacity`). `GET /api/v1/logs?limit=&level=` serves it to the Activity log card on the Operations view, so diagnosing a stuck file does not require container log access. It is deliberately not persisted; the durable record is the operation history.
- Manual automation: `POST /api/v1/automation/run` only queues the existing single-reader worker when automation is enabled and idle, and requests a full reconcile. The Running event card displays the periodic countdown and disables duplicate manual triggers.
